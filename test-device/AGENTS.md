# test-device/AGENTS.md

`test-device/` で端末を動かすテストを書く、直す、流すときの指示です。
リポジトリルートの `AGENTS.md` と一緒に読んでください。テストの一覧と、環境の用意のしかたは
[README.md](./README.md) にあります。

## 待つところ: 1 つずつ待たず、まとめて待つ

端末の画面はひとつなので、**画面の操作は順番にしかできません**。
でも、**転送が終わる・ファイルが届く・ログが出る、を待つところは、あとに回してまとめて待てます**。

1 マスずつ「操作 → 届くまで待つ」を繰り返すと、失敗したマスの数だけタイムアウトを待つことになります。
36 マスのテストで失敗が多いと、それだけで 1 時間を超えました（2026-09-29、#140）。

- **操作するところと、確かめるところを分けます**
    - 操作のあいだは、何を確かめるかを記録しておくだけにします
    - 確かめるのは、操作が全部終わってから、**ひとつの締め切り**でまとめて行います
    - こうすると、失敗がいくつあっても待つのは 1 回分です。操作しているあいだに裏で転送も進みます
    - 例: `drive/72-a-folder-onto-every-storage.sh` の `judge_the_transfers()`
- **まとめて確かめるときは、どの結果がどのマスのものかを、順番に頼らずに決めます**
    - 同じフォルダを同じところへ 2 回コピーすると、`(1)` `(2)` の番号は終わった順につきます
    - 72 では、グループに入っているかどうかでマスと突き合わせ、ひとつの結果は 1 マスにしか渡しません
- 画面を見なければ確かめられないもの（ピッカーが断る理由を出す、など）は、その場で確かめます

## タイムアウト: 測ってから決める

- **タイムアウトは、成功したときに実際にかかった時間を測ってから決めます**
    - 勘で「長めに 3 分」とすると、失敗のたびにその 3 分がまるごと足されます
    - 測った時間をテストの出力に出しておくと、次に決め直すときの手がかりになります
      （72 は「操作に何秒、判定に何秒」を `note` で出しています）
- **テストが思ったより長いときは、まずテスト自身の待ち方を疑います**
    - 遅いのはアプリや外のサーバではなく、失敗の数 × タイムアウトだった、ということがありました
    - 流しているあいだも出力を見て、失敗が並んでいたら止めて直します

## 一部のマスだけを流す

表をなぞる長いテストは、直しているマスだけを流せるようにしておきます。
72 は `FIXTURE_ONLY_CELLS="2 3"` で、そのマスだけを流します（共有を読む 5 分はかかります）。
